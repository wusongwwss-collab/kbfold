# KBFold（知识库整备台）· 宿主无关用法说明书

> 本文件写给「任何支持 MCP 的宿主 / AI 代理」看：无论你运行在哪种宿主环境里，按本说明即可接入 KBFold 并正确使用其工具面。

## 是什么

KBFold 是一个**本地知识库整备台**：把散乱的项目资料编译成有索引、可检索、可回滚的知识库目录。

- **先看后动**：`plan` 只预演不落盘，`apply` 才写盘，`undo` 整批退回；每一步记进追加式日志，历史永不被改写。
- **不猜**：规则打平、证据不足、置信低于阈值 ⇒ 一律进 `_inbox/` 并附候选与理由。
- **零风险默认**：只读扫描、不读文件内容（只读元信息）、除本地嵌入模型外零外连、删除能力不存在。
- 零第三方依赖、零 API key、零账号；断网可用。

## 五个只读工具

| 工具 | 作用 |
| --- | --- |
| `kb.scan` | 只读扫描指定根目录，产出现状统计（可判定 / 待归 / 被排除）、乱度指标与疑似知识库清单（每条带置信与原因） |
| `kb.plan` | 生成整备方案预演：adopt（既有目录纳入）/ mkdir（新建）/ shift（平移）/ rearrange（重排）四张分列清单，每条带理由与置信；全程零写入 |
| `kb.search` | 三路检索（语义 / 全文 / 关键词）融合，每条结果带 `[n]` 引用编号，可回溯到文件与位置 |
| `kb.explain` | 回答「这个文件为什么被放在这里」（读台账里的 `reason` 字段，返回命中层级与依据） |
| `kb.validate` | 校验规则文件结构：黑名单命中、字段错误、版本不符逐条标出 |

五个工具**全部只读**：不会写盘、不会移动文件、不会发起外连。

## 在支持 MCP 的宿主中配置

MCP 服务器是 **stdio 形态**：宿主负责拉起进程、通过标准输入输出通信、退出时回收。

```json
{
  "mcpServers": {
    "kbfold": {
      "command": "npx",
      "args": ["-y", "kbfold", "mcp"]
    }
  }
}
```

（本地开发场景也可指向仓库内的 MCP 服务器脚本，用 Python 3.10+ 直接拉起；无需安装任何依赖。）

配置保存后**重启宿主**，在工具列表里确认 `kb.scan` / `kb.plan` / `kb.search` / `kb.explain` / `kb.validate` 真实可见——以宿主工具列表出现为准，配置文件保存成功不等于接入成功。

## AI 边界：apply / undo 归 CLI，刻意不注册为工具

**`apply`（落盘执行）与 `undo`（回滚）只在命令行存在，MCP 面刻意不提供。** 这是安全边界，也是产品人格：AI 只能预演，落地由人执行。

你要做的：

1. 用 `kb.scan` / `kb.plan` 完成扫描与预演，把方案（含平手清单）呈现给用户；
2. 用户在**命令行**自行执行 `kbfold apply <路径>`（首次建议 `--rename-only`：只改名不搬家）；
3. 需要退回时，用户在命令行执行 `kbfold undo <批次号>`。

不要试图绕过这条边界，也不要替用户「顺手」执行写盘命令。

## 引用纪律（调用 `kb.search` 后必须遵守）

1. 每条结论后紧跟 `[n]`，不得改动顺序或另编号。
2. 只有确实出现在返回结果里的内容才能标 `[n]`。
3. 无命中必须明说「知识库中没有找到相关内容」，禁止推测补全。
4. 结果不足如实说「仅找到 2 条」，不得凑数。
5. 引用低置信片段须注明「待人工确认」。

## 模板与规则在哪

- 规则文件：资料目录根部的 `kbfold.yml`（人写、人读；全量示例与逐字段中文注释见仓库 `packs/kbfold/rules.example.yaml`）。
- L0 通用模板：仓库 `packs/kbfold/templates/` 下两件——项目阶段视图（00–07 八段）与文件类型视图（01–12 十二类），全字段中文注释，可改、可 diff、可分享。
- 库产物：资料目录旁的 `.kb/`（删掉即复原；别提交进 git）。
- 改规则流程：改 YAML → `kb.validate` 校验 → 重跑 `kb.plan` 看差异 → 用户在 CLI 执行 `apply`。

## 反馈开关

- **默认关闭**；第一次 `plan` 成功后宿主会收到一次询问回调（由宿主对话框承载），之后不再问。
- CLI 形态：`kbfold feedback on | off | show`（`show` 逐条列出上行记录）。
- 开启后上行只有三样统计与结构信息：被拒绝的归档建议（不含文件名）、模板命中计数、目录结构指纹（只 hash 不报名）。**永不上行**文件名、目录原名、文件内容、路径原文。详见 `docs/FEEDBACK.md`。

## 常见问题

1. **需要联网或 API key 吗？** 不需要。判定全在本地完成；断网可跑通全部流程。`kbfold audit` 会列出本次运行的全部外部端点，正常为空（或仅本地嵌入模型端口），零外连可当场自证。
2. **它会删用户的文件吗？** 不会。代码里没有删文件的调用，可自行检索验证；`trash/` 里是副本快照，清理副本也不影响源文件。
3. **`_inbox/` 会自己清空吗？** 不会。它是待办队列：处理掉一批（改规则或手动安置）再跑 `kb.plan` 才会变短。不自动清空，因为自动清空等于自动猜。
4. **为什么两条规则打平就一个都不选？** 平手时任何选择都是抛硬币，而抛错的代价是在几千个文件里找那一份。所以两个候选都列进 `_inbox/`，让用户决定。
5. **用户改了规则没生效？** 按顺序查：① `paths[].match` 的基准目录是 `root`，不是规则文件所在目录；② 通用目录名黑名单（`data`、`config`、`docs` 等）在启动时就被拒了，看 `kb.validate` 的输出；③ 多条命中时被更具体的规则覆盖了，用 `kb.explain` 看文件到底命中哪条。
